# Double-blind FA QA · Round 03

## 一句话结果

证据完整性与权威冲突测试从“产品能接收文件但看不见关键控制缺陷”，迭代到“17/17 项限定回归通过且继续 fail closed”。这代表本轮证据控制能力修复成功，不代表企业材料可信、产品总体验满分或任何投资结论。

## 测试角色与隔离

- 企业角色只看到 Round 3 提问，提交的企业资料与补件全部为 **Synthetic**。
- 初始 FA 只看到企业首包和运行中的产品，不读取补件、修复方案或后续轮次。
- 工程诊断只读取 Round 3 失败材料、测试结果与产品代码。
- 修复后 FA 使用全新 workspace 和当前代码独立重放；复用了既有安全/证据 specialist thread，但该 specialist 未生成 Round 3 数据、未实施修复，且报告中已披露。
- 真实部分仅限本地 HTTP、浏览器、文件哈希、case ID、诊断、测试与端口遥测。

## 初始盲测

初始 case 为 `case-20260804-405f4af91c`。原生控制覆盖 4/10（诊断覆盖度，不是公司或产品评级）：系统保留了候选证据和人工复核边界，但没有识别声明哈希 mismatch、权威/版本/批准/签字分轴、底层哈希重复、跨文件冲突，并因通用 `as_of_date` 错误触发财务预检。

FA 留下 8 个逐字问题，分别覆盖：哈希与重复、P2601 验收、P2602/P2603 订单、forecast 权威版本、现金证明、cap table、IP 权利和东南亚许可。

## 企业补件与使用记录

企业角色逐一回应全部 8 个问题，没有补造不存在的已签署/权威文件：

- `answered`: 1

响应覆盖率为 100%；按公开公式计算的证据包进度为 31.25%。两者都只是 FA 工作流完整度，不是企业评分、投资/信用/综合风险评级或建议。企业撤回了无法证明的 P2601、订单、现金、IP 与许可主张，并保留相应证据缺口。

修复前补件基线真实复现了三项传输/状态问题：21 文件超过上限、原生 `.jsonl` 被拒绝、相同内容不会折叠；系统也没有把补件绑定到 R03 问题或形成持久化补件状态机。

## 工程问题与修复

工程复核确认 5 个相互独立的缺陷：

1. manifest 声明哈希未与实际上传对账；
2. 权威、版本、批准、生效、签字和时点未独立建模；
3. 同一底层内容可能因文件名不同而重复计数；
4. 有稳定键的跨文件矛盾未暴露；
5. 通用 `as_of_date` 对非财务资料造成财务预检假阳性。

修复后新增确定性的证据控制层，保留全部来源与别名，不自动修正、不自动选权威、不自动判真；同时收紧财务 schema 适用性，并将人工复核动作投影到 Dashboard。

- 两份重复 07 为 1 个候选证据单元、2 个别名、0 accepted；P2602 底层 payload 缺失，证据计数为零。

真实 Chromium 回放显示证据控制卡片、人工下一步、冲突与候选 receipt；定位按钮有效、控制台无错误。Axe 修复后为 0 violations / 0 incomplete。完整 Python、Ruff、Node 估值测试和 diff whitespace 门禁在本轮提交前再次执行。

## 仍未实现或保留的问题

- 补件中心的持久化状态机、企业端账户/权限、逐版本提交和人工接受动作仍是路线图，不应由本轮候选 receipt 冒充。
- 顶层 legacy `next_action` 与 dashboard 投影存在非阻断差异，需后续统一。
- 本轮只证明合成冲突包下的证据控制回归；仍缺真实企业数据、真实法律/财务文件和真实 FA 团队验证。
- 本轮没有扩张产品能力边界：两项端到端财务维度不变，ARL/ESG/清洁技术影响/出海仍按既有证据框架描述。
